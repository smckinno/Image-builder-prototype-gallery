Image Builder — input patterns

Clickable exploration: chip/label input vs PatternFly Field Builder

Prototype · not production

What you’re deciding

For Image Builder “add multiple values” fields, which interaction pattern should we standardize on — and when should we switch patterns based on the shape of the data?

Pattern A · current

Chip / label input group

One text field. User types a value, then presses Enter or clicks Add. Values become removable chips inside the field.

  • Best for single, short, independent values (kernel args, packages, SSH keys as tokens)
  • Compact — many values in little vertical space
  • Risk: Enter-to-add can conflict with form submit / accessibility expectations
  • Weak for paired fields (name + ID) — chips hide structure
Pattern B · PF Field Builder

Field Builder rows

Explicit rows with column labels. Add … appends a row; each row has a remove control. Matches PatternFly Field Builder.

  • Best for structured / multi-field entries (group name + ID, user + UID, etc.)
  • Clearer editability — values stay as inputs, not tokens
  • Uses more vertical space
  • Overkill for a long list of one-word tokens
Working hypothesis to test in this prototype: use chips for single-value lists; use Field Builder when each entry has 2+ fields (or when users need to edit a value after adding it without deleting the chip).
